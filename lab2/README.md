# Лабораторна робота №2 — Тестування протоколу ARP

**Варіант 2** (остання пара цифр % 3 = 2): додати статичний запис у ARP-таблицю, пропінгувати інший пристрій і відстежувати трафік у Wireshark.

## Оточення
- Мережевий адаптер VM у режимі **Bridged** (Wi-Fi)
- Ubuntu 24.04.5 LTS ARM64 у UTM (QEMU), користувач `diana_siukalo@ubuntu-kpi`
- VM: `192.168.31.11/24`, інтерфейс `enp0s1`, MAC `82:fa:c1:02:69:56`
- Цільовий пристрій — маршрутизатор `192.168.31.1`, MAC `cc:d8:43:cb:6b:eb`
- Wireshark (захоплення без root, користувач у групі `wireshark`)

## Запуск
```bash
bash lab2_auto.sh            # ціль за замовчуванням — шлюз
```
`lab2_arp.sh` — інтерактивна версія з паузами під скріншоти.
Скрипт виконує всі кроки підряд, робить паузи для скриншотів і пише весь вивід у `~/lab2_arp_<дата>.log`.

## Кроки
1. Очищення ARP-кешу → `ping` → ARP Request / ARP Reply у Wireshark
2. Перевірка оновлення ARP-таблиці (`arp -a`, `ip neigh`)
3. **Варіант 2:** `sudo arp -s <IP> <MAC>` → маркер `PERM` → `ping` без жодного ARP Request
4. **Власний тест-кейс:** статичний запис із хибною MAC → 100% packet loss → `arp -d` → зв'язок відновлено

## Тест-кейси

### ARP-TC-01 — статичний запис у ARP-таблиці
| Поле | Значення |
|---|---|
| Передумови | VM і ціль в одній підмережі; MAC цілі відома; динамічний запис видалено; Wireshark, фільтр `arp` |
| Кроки | 1) `sudo arp -s <IP> <MAC>` 2) `arp -a` 3) `ping -c 5 <IP>` 4) аналіз у Wireshark |
| Очікувано | Запис із `PERM`; ping успішний; немає `Who has <IP>?` від VM |
| Фактично | `192.168.31.1 at cc:d8:43:cb:6b:eb PERM`; ping 5/5, 0% loss; ARP Request від VM відсутні |
| Статус | PASS |
| Післяумова | `sudo arp -d <IP>` |

### ARP-TC-02 — статичний запис із неправильною MAC (власний)
| Поле | Значення |
|---|---|
| Передумови | Як у TC-01; Wireshark, фільтр `arp \|\| icmp` |
| Кроки | 1) `sudo arp -s <IP> 02:00:00:00:00:01` 2) `ping -c 5 -W 1 <IP>` 3) аналіз у Wireshark 4) `sudo arp -d <IP>`; `ping -c 3 <IP>` |
| Очікувано | Крок 2: 100% packet loss, ICMP на хибну MAC без відповіді, ARP Request немає. Крок 4: зв'язок відновлено |
| Фактично | 5 transmitted, 0 received, 100% packet loss; після `arp -d` — 3/3, 0% loss |
| Статус | PASS |
